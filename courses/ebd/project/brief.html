1The project

Your team builds a working web application with the full MERN stack: a React front end, an Express API on Node.js, and a MongoDB database.

You register your team, your topic and your repository through a form. The form and the list of topics will be announced.

  • Teams of 5 or 6 students.
  • One use case per member, so 5 or 6 use cases in total.
  • Each member builds their use case end to end, front end and back end, and is graded on it.
  • Registration and login are mandatory, and count as one of the use cases.

What a use case is

A use case is something a user does, from start to finish: a user creates a listing, a user books a stay, an admin removes a review. Each one has all four parts:

  1. a page or form in React,
  2. that calls one or more routes of your API,
  3. which read or write your MongoDB database,
  4. and the user sees the result.

Every use case must change data: create, update or delete something. A page that only displays data belongs to the use case it supports, and does not count on its own.

2Technical requirements

This is the minimum. Everything here is taught in the labs.

AreaRequirement
RepositoryOne GitHub repository per team, with every member as a collaborator. At its root: a backend/ folder, a frontend/ folder and a README.md.
Back endExpress and Mongoose on MongoDB Atlas, organised as in Lab 5, Part 2: server.js, db.js, models/, controllers/, routes/, and a middleware/ folder for authentication.

Secrets.env is never committed. Commit a .env.example with the variable names and no values.
User interfaceUsable, responsive and clean. There is no design prize, but common sense is expected: readable, consistent, and working on both a laptop and a phone.
GitEach member commits their own work, from their own GitHub account. The history is how we see who built what.

4Submission 1: the plan

Due Thursday 12 November 2026, 23:59. Create your team's repository and push a README.md to its main branch, following the template that comes with this brief. It contains:

  1. The team: each member's name, student ID, tutorial group and GitHub username.
  2. The idea: what the application is, who it is for, and what problem it solves.
  3. The full feature list: everything the complete product could do, beyond this course.
  4. The 5 or 6 use cases you will build, registration and login included. For each: what the user does, what they see, and what is stored.
  5. Who owns each use case: one member per use case.
  6. The data model: the Mongoose schema of each model you plan to use.

Approval

We review every plan and reply by Thursday 19 November. The answer is either approved, or changes requested, with what to change. Changes are requested at most once. Update your README by Monday 23 November, 23:59; that version is approved.

Your approved plan is your contract. It is exactly what you build, and exactly what you are graded against: nothing less, and no surprise extras in its place. Changing it after approval needs our written agreement.

Choose a scope you can finish. Five use cases that work beat ten that half-work. We may ask you to cut a use case that is too big, or grow one that is too small.

7AI tools

You may use AI tools. Before you do, know how they affect your grade.

  • You build what you planned. Your approved plan is what you are graded against, with AI or without it.
  • You are graded on understanding. In the discussion you explain your use case line by line. Code you cannot explain counts against you, whoever wrote it.
  • AI raises the bar. AI-written code is usually more complex than what you would write yourself, and the more advanced your project, the more we expect you to explain. A polished project you can't explain scores lower than a simple one you understand completely.

If you can build it yourself, that is usually the safer way to a good grade.

8Grading

Your grade has two parts:

  • Team: the application as a whole. Does it run, does it deliver the approved plan, does it meet the technical requirements, and is the README complete?
  • Individual: your own use case. Does it work end to end, is the code clean, and do you understand it and how it fits into the rest of the application?

9Rules

  • A committed .env is a leaked password: a penalty.
