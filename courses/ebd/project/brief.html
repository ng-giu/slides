1The project

Your team builds a web application with React (front end), Express on Node.js (back end) and MongoDB (database). This is the stack you use in the labs.

  • Teams of 5 or 6 students. Members can be from different tutorial groups.
  • Your team chooses its own idea. Take inspiration from your other courses and projects (for example, FinTech). The idea is approved together with your plan (Submission 1).
  • The team builds one use case per member: 5 use cases for a team of 5, 6 for a team of 6.
  • Each member builds their own use case end to end, front end and back end, and is graded on it.
  • Registration and login is mandatory, and counts as one of the use cases.

What a use case is

A use case is one thing a user does, from start to finish. For example: a user creates a listing, a user books a stay, an admin removes a review. Each use case has all four of these parts:

  1. a page or form in React,
  2. that calls one or more routes of your API,
  3. which read or write your MongoDB database,
  4. and the user sees the result on the page.

Every use case must change data: create, update or delete something. A page that only displays data is part of the use case it supports. It does not count as a use case on its own.

3Technical requirements

Everything in this table is taught in the labs.

AreaRequirement
RepositoryOne public GitHub repository per team, with every member added as a collaborator. At its root: a backend/ folder, a frontend/ folder and a README.md file.
Back endExpress and Mongoose on MongoDB Atlas, organised as in Lab 5, Part 2: server.js, db.js, and the folders models/, controllers/, routes/ and middleware/.
DataA Mongoose schema for every model. Create, read, update and delete on at least two models.
Front endReact with Vite. Several pages with React Router, built from your own components. All data comes from your API: nothing is hard-coded in the final version.
AuthenticationRegister and log in, as in Lab 9. Passwords are hashed with bcrypt, never stored as plain text. A JWT identifies the logged-in user. API routes that need a user check the token, and pages that need a user redirect to the login page.
SecretsNever commit your .env file. Commit a .env.example file in backend/ that has the same variable names, with no values.
User interfaceReadable and consistent, and usable on both a laptop and a phone. There are no marks for visual design beyond that.
GitEach member commits their own work from their own GitHub account, the one written in your README. We use the commit history to see who built what.

Set up your README from the template

The template is the file README-template.md, on the CMS next to this document. One member does these steps, then pushes:

  1. Clone your team's repository to your laptop, if you have not yet: git clone followed by your repository's link.
  2. Download README-template.md from the CMS.
  3. Rename it to exactly README.md: capital README, small .md.
  4. Move it to the root of your repository folder, next to backend/ and frontend/, not inside either of them. If you have not created backend/ and frontend/ yet, the README is the only thing in the folder for now: 
    your-repository/
├── backend/
├── frontend/
└── README.md
  5. Open it in VS Code. Press Ctrl+Shift+V (Cmd+Shift+V on a Mac) to see a preview of how it will look on GitHub.
  6. Commit and push it to main. Open your repository on GitHub: the README is shown under the list of files.

Then the whole team fills it in, and pushes again. The rules for filling it in:

  • Replace everything in [square brackets] with your own text, brackets included.
  • Delete the lines that start with >. They are instructions for you, not part of your plan.
  • Keep the section headings and their numbers as they are. Do not rename, reorder or delete sections: we read every team's README in the same order.
  • A team of 5 deletes the last row of each table in sections 1, 3.2 and 4.
  • Leave section 6 as it is until Submission 2.

6Milestones

Two milestones between the plan and the final code. You do not submit anything for them: our script clones your repository at the deadline and checks it. The checks are the same ones we run on the final code (Section 7), so passing them early means fewer surprises at the end.

Milestone 1: the project runs · Thursday 19 November, 23:59

  • backend/ starts with npm install, then npm start, on port 3000, using a .env with our own values.
  • GET http://localhost:3000/api/health answers status 200 with the body { "status": "ok" }.
  • frontend/ starts with npm install, then npm run dev. Its home page (/) has an element with id="project-name" that shows your project's name.
  • Every member has at least one commit on main, from their own GitHub account.

Milestone 2: registration and login work · Thursday 3 December, 23:59

  • Everything in Milestone 1 still works.
  • POST /api/auth/register with the JSON body { "name", "email", "password" } creates a user and answers status 201 with a body that contains a token.
  • POST /api/auth/login with { "email", "password" } answers 200 with a token for the right password, and 401 for a wrong one.
  • The user is saved by a Mongoose model named User, and its password field holds the bcrypt hash, not the password itself.
  • Since Milestone 1, every member has new commits in both backend/ and frontend/: their own use case is under way.

10Grading

Your grade has two parts:

  • Team: the application as a whole. Does it pass the automatic check, does it deliver the approved plan, does it meet the technical requirements, and is the README complete? The milestones are part of this grade.
  • Individual: your own use case. Does it work end to end, is the code clean, and can you explain it and how it connects to the rest of the application?
