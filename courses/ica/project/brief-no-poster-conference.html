1The project

Your team selects a creative, feasible web application idea and takes it through the full Information & Communication Architecture lifecycle: user stories, acceptance criteria, and wireframes (PD1), a clickable Figma UI prototype (PD2), and a working multi-page HTML, CSS & JavaScript website with a live API component (PD3), accompanied by a final report, an A1 printed poster, and a live team presentation.

  • Teams of 5 or 6 students. Each team is assigned an official Team ID and designates one member as the main point of contact to coordinate with their TA and submit on behalf of the team.
  • One distinct feature per member (5 or 6 core features in total).
  • Each member owns their feature end to end across every stage of the project, and is graded on both team cohesion and individual execution.

What end-to-end feature ownership means

Clear accountability ensures fair grading. Every team member is individually responsible for one complete feature from start to finish:

  1. writing its user stories and acceptance criteria (at least 2 user stories for their feature, each with at least 3 testable acceptance criteria),
  2. sketching its low-fidelity wireframes,
  3. designing its high-fidelity Figma screens and interactive prototype connections, and
  4. coding its HTML & CSS page(s) (and interactive JavaScript/API logic) in the team repository.

Every member must write their full name next to the sections, screens, and pages they worked on in PD1, PD2, PD3, and the Final Report.

4Stage details: PD1, PD2 & PD3

4.1 PD1 — Concept, User Stories, Acceptance Criteria & Wireframes (20%)

Your PD1 document (submitted as a PDF/Word document and summarized in your repository's README.md) must contain three parts:

  1. Web App Idea Document:
    • The application name, core concept, and purpose.
    • Target users and the specific real-world problem the application solves.
    • The 5–6 core features (one distinct feature assigned to each team member, with the member's full name and student ID).
  2. User Stories & Acceptance Criteria (as taught in Lab 1):
    • At least 2 user stories per feature (10–12 user stories minimum for the team), written in standard Agile format: “As a [type of user], I want [an action or goal] so that [a benefit or reason].”
    • Acceptance Criteria (AC) for every user story: Write at least 3 clear, testable acceptance criteria per user story that define the objective pass/fail boundaries of the feature—covering both the happy path flow and at least one negative/validation scenario (e.g., empty input, invalid filter, or out-of-range value). Do not list generic Definition of Done (DoD) items as acceptance criteria.
  3. Wireframes:
    • Low-fidelity wireframes for the Home page plus every member's feature page(s).
    • May be clean hand sketches (photographed/scanned clearly) or digital wireframes (Figma), showing layout structure and content placement before visual styling.

4.2 PD2 — Clickable Figma Prototype (20%)

Turn your PD1 wireframes into a high-fidelity, interactive UI prototype in Figma (building on Labs 2–4):

  • Visual UI Consistency: A unified color palette, typography scale, spacing system, and reusable components across all members' screens.
  • Information Architecture (IA): Clear site hierarchy, navigation bar/menus, breadcrumbs or back links, and logical user flows between the Home screen and every feature screen.
  • Clickable Prototype: Interactive hotspot connections in Figma Prototype mode so a user can click through the entire application flow from start to finish.
  • What to submit: Your shareable Figma prototype link (with view permissions set to Anyone with the link can view) plus exported high-resolution PNG/PDF screens labeled by feature owner.

4.3 PD3 — Multi-Page Website & Live JavaScript API (20%)

Implement your design as a real, working multi-page web application using HTML, CSS, and JavaScript (building on Labs 5–10):

AreaRequirement
HTML & CSSSemantic HTML5 pages (index.html plus each member's feature .html page) styled with external CSS stylesheet(s) (Flexbox, Grid, clean typography, hover states, and responsive layout).
NavigationWorking <a href="..."> navigation across all pages—no broken links or isolated pages.
JavaScript & DOMInteractive client-side behavior using DOM selection, event listeners (addEventListener), and dynamic content updates.
Live API ComponentYour website must integrate at least one live public API using fetch() and render the returned JSON data into the DOM (as practiced in Lab 10). Examples include:
  • Weather API (e.g., Open-Meteo)
  • Maps / Geolocation (e.g., OpenStreetMap / Nominatim)
  • Currency Exchange API, News API, Recipe/Food API (DummyJSON / TheMealDB), Quotes/Facts API, or any free public REST API fitting your app's theme.
GitHub & ArchiveMaintain your code in one team GitHub repository where each member commits their own feature pages, and submit both the GitHub repository link and a compressed .zip folder containing all project files (.html, .css, .js, images, and README.md).

5Final Report, Printed Poster & Presentation

5.1 Final Report (10%)

Submit a well-formatted PDF report that documents your entire project from concept to code. It must include:

  1. Cover Page & Table of Contents (with team number, member names, IDs, and tutorial groups).
  2. Introduction & App Concept: the idea, target audience, and problems solved by your app.
  3. All User Stories & Acceptance Criteria: grouped by feature, with each user story's acceptance criteria and the responsible member's name next to their part.
  4. Wireframes: all PD1 wireframes.
  5. Figma Screens: high-resolution exports of all PD2 UI screens and navigation flow.
  6. Website Screenshots: screenshots of the working HTML/CSS pages in the browser.
  7. Explanation of APIs Used: which public API endpoint(s) you called, what JSON data they return, and how your JavaScript code displays it on the page.
  8. Roles & Contributions Table: exact breakdown of what each team member designed and coded.
  9. References: proper citation of all external resources, APIs, icons, fonts, or articles used.
  10. Appendix — AI Prompts Used: a complete log of all AI prompts used by any team member during the project.

5.2 Printed A1 Poster (5%)

Every team designs an A1 portrait (vertical) poster (59.4 cm × 84.1 cm / 23.4 in × 33.1 in) to be displayed in the BI corridor after presentation week.

  • Required content on the poster:
    • Application name and logo/branding.
    • Core idea, purpose, and the problem solved by the web app.
    • Key high-resolution Figma/website screens (clean, sharp, never pixelated or black-and-white).
    • Full names (first and last name) and Student IDs of all team members.
    • Course name (BINF 301), Instructor name (Dr. Nourhan Hamdi), and your TA's name.
  • Visual design guidelines:
    • Less text, more visuals: avoid long paragraphs—use diagrams, icons, callouts, and high-impact UI screens.
    • Review & approval before printing: your team's point of contact must share the digital poster design with your TA for feedback and approval before printing.
    • Do not print before getting the green light! Once approved by your TA, print the poster in full color on foam cardboard.

5.3 Final Presentation Day (15%)

Presentations take place in Week 13 (12–17 December) according to the published Presentation Slots sheet (day, time, and room per Team ID).

  • Format: 8–10 minutes for the team presentation, followed immediately by 8–10 minutes of Q&A and discussion.
  • What to demonstrate:
    1. The app idea and problem solved,
    2. The clickable Figma prototype,
    3. The live working multi-page HTML/CSS website,
    4. A live demonstration of the JavaScript API component, and
    5. Each member explaining their own feature (screens, HTML/CSS structure, and JavaScript code).
  • Comprehensive awareness: every member must be aware of the entire presented material—including how their teammates' pages and the shared CSS/JS connect together.
  • Have screenshots or a short screen recording ready as a backup in case of an internet outage during the live API demo.

6Use of AI tools

You may use AI tools to assist with generating or refining HTML, CSS, JavaScript, or visual assets ONLY IF all three conditions below are met:

  1. You fully understand the code: During the 8–10 minute Q&A discussion, you will be asked to explain your HTML, CSS, and JavaScript line by line. Code you cannot explain counts against your individual grade, regardless of how it looks.
  2. You document all AI prompts in the Report Appendix: Every prompt used by any member must be included in the Appendix: AI Prompts Used section of the Final Report.
  3. You remain responsible for the final output: AI is a tool, not a replacement for your design. Your website must faithfully implement your team's approved PD1/PD2 architecture and features.

A clean, well-structured website that you understand completely always scores higher than complex AI-generated code that you cannot explain.
